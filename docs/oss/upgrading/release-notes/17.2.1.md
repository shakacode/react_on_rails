# React on Rails 17.2.1 Release Notes

17.2.1 is a patch release for 17.2.0. Its main fix keeps each request's hydrated Redux stores separate when the Pro
Node Renderer serves concurrent server renders. It also carries security updates for React Server Components (RSC)
apps and the Node Renderer.

Until 17.2.1 final ships, use the exact matching gem and npm prerelease versions. For example, Ruby uses
`17.2.1.rc.2`, while npm uses `17.2.1-rc.2`.

For the complete list of changes, see the [CHANGELOG](https://github.com/shakacode/react_on_rails/blob/main/CHANGELOG.md).

## Upgrading from 17.2.0 to 17.2.1

Update your gem and npm package versions:

```ruby
# Gemfile
gem "react_on_rails", "17.2.1"
```

```json
// package.json
{
  "dependencies": {
    "react-on-rails": "17.2.1"
  }
}
```

**Pro users:** Use `react-on-rails-pro` instead of `react-on-rails` in package.json, and `react_on_rails_pro` instead
of `react_on_rails` in your Gemfile. See the [Pro upgrade guide](../../../pro/updating.md) for details.

Then run `bundle install` and your package manager's install command.

## Action required for Pro applications

### Upgrade the Node Renderer and JavaScript packages together

On the Pro Node Renderer, `ReactOnRails.getStore()` called after an `await`, in streamed content, or in an RSC
Client Component provider could return another concurrent request's store. One user's page could then render with
another user's state. Each render request now gets its own hydrated store registry. See
[Issue 5124](https://github.com/shakacode/react_on_rails/issues/5124) and
[PR 5133](https://github.com/shakacode/react_on_rails/pull/5133).

- Upgrade `react-on-rails-pro-node-renderer` and your React on Rails JavaScript packages in the same deploy. The
  per-render registry needs both sides.
- Move any `setStore` call at module scope of your server bundle into per-render hydration. Register store
  generators at module scope, but hydrate user-specific stores from render props. See the
  [Redux store API](../../api-reference/redux-store-api.md).
- Async work started inside a render, such as a promise chain or a timer when `RENDERER_STUB_TIMERS=false`, keeps
  that render's stores after the render finishes.
- Browser store APIs and page lifecycle behavior are unchanged.
- If request scoping causes a problem, set `isolateHydratedStores: false` in the renderer configuration, or
  `RENDERER_ISOLATE_HYDRATED_STORES=false`, to restore the shared registry temporarily, and
  [report the problem](https://github.com/shakacode/react_on_rails/issues). See
  [Node Renderer JavaScript configuration](../../building-features/node-renderer/js-configuration.md).

### Refresh `react-server-dom-webpack` in RSC apps

React published [GHSA-xqc2-xf4c-x3h3](https://github.com/react/react/security/advisories/GHSA-xqc2-xf4c-x3h3)
(critical, remote code execution) and
[GHSA-h3gv-c5rc-p453](https://github.com/react/react/security/advisories/GHSA-h3gv-c5rc-p453) (high, denial of
service) on 2026-10-14 against `react-server-dom-webpack` 19.0.0 through 19.3.0. React on Rails does not pin that
package. Fresh installs already resolve a fixed version, but an existing lockfile keeps the old one.

- Update `react`, `react-dom`, and `react-server-dom-webpack` together to 19.3.1, or all three to 19.2.9 on the 19.2
  line, and commit the refreshed lockfile. The patched `react-server-dom-webpack` peers on the matching React version.
- Check what your lockfile resolves with `pnpm why react-server-dom-webpack` (or the npm or Yarn equivalent), or
  run `bundle exec rake react_on_rails:doctor`, which now warns about affected copies, including pnpm copies
  installed from a tarball, a git repository, or a local file.
- Apps that stay on React on Rails 17.2.0 can apply the same dependency update; it needs no gem change.

## Other fixes

- **Node Renderer requires `fastify` 5.12.6 or later**, so an existing lockfile cannot keep a `fastify` affected by
  the 5.12.x security releases. Node 18.19 apps that use the documented Fastify 4 override keep it, but no Fastify 4
  release fixes the authentication and request-validation bypasses, so move to Node 20 or later.
- **Fragment-cached components refresh CSP nonces on cache hits**, so CSP no longer blocks hydration, console
  replay, or streaming scripts from a `cached_*` helper. Do not embed request nonces in cached props or text. If
  you override `normalize_cached_pro_attribution` or `normalize_cached_pro_attribution_html`, accept and forward the
  new `cached_csp_nonce` parameter. See [CSP caching caveats](../../../pro/strict-csp.md#caching-caveats).
- **The RSC generator installs React from `~19.3.1`**, so new RSC apps cannot resolve React 19.3.0.
- **Inline RSC payloads suppress console replay outside development and test** whenever `renderingError` is
  present.
- **Rspack server bundles no longer write a stray `ssr-generated/manifest.json`.** Existing Rspack apps can apply
  the same plugin filter in `config/rspack/serverWebpackConfig.js`; see the
  [CHANGELOG](https://github.com/shakacode/react_on_rails/blob/main/CHANGELOG.md) entry.
- **`unstable_cache` no longer throws `BUILD_ID not set`** on RSC payload requests that reach a fresh renderer
  worker.
