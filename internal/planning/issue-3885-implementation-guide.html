Issue #3885: cacheSignal
Implementation Guide

React 19.2's cacheSignal() lets RSC components cancel in-flight data work when a render is abandoned. The abort wiring is already in place (PR #4093). This issue validates the chain works end-to-end and documents the pattern.

1 The Existing Abort Chain (PR #4093)

When a client disconnects mid-stream, the abort propagates through 5 layers. All of this is already shipped. cacheSignal works because React settles it automatically when PipeableStream.abort() fires.

Key insight: We don't need to wire cacheSignal ourselves. React does it automatically when PipeableStream.abort() fires. PR #4093 already ensures abort fires on disconnect. Our job is to prove it works (test) and teach users the pattern (docs).

2 How cacheSignal() Works in Our Stack

The signal is available through the React 19.2.7 installed under react-server-dom-webpack. It is NOT available from the root react package (which is 19.0.7).

The User-Facing Pattern

Server Component // This runs in the RSC bundle (react-server condition) import { cache, cacheSignal } from 'react'; const fetchProduct = cache(async (id: string) => { const signal = cacheSignal(); const res = await fetch(`${railsApiUrl}/products/${id}`, { signal }); return res.json(); }); export default async function ProductPage({ id }) { const product = await fetchProduct(id); return <div>{product.name}</div>; }
What happens on client disconnect: abort wiring → PipeableStream.abort() → React settles cacheSignal() → fetch() throws AbortError → DB/API call cancelled. Zero wasted work.
